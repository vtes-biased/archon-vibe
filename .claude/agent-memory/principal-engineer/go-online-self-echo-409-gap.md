`go_online` (backend/src/routes/tournaments.py ~1726) saves `offline_mode=false` and `broadcast_precomputed()`s BEFORE returning the HTTP response; `broadcast_precomputed` (broadcast.py) fans out to ALL connections. The initiating device used to receive its own `offline_mode=false` echo over SSE while local `isOffline(uid)` was still true (the HTTP response that runs `clearOfflineState` hadn't resolved) → the three `lostOfflineLock` call sites in sync.ts (~218 snapshot, ~382 single, ~443 batch) fired a spurious "lock lost" toast + premature clearOfflineState.

**Shipped fix (two layers, both intentional — neither redundant):**
- **Server self-exclusion (source kill):** `SSEConnection` has `device_id`; `/stream` takes a `device_id` query param (sync.ts always sets `getDeviceId()`); `broadcast_precomputed(bd, *, exclude_device_id=...)` skips connections whose `device_id == exclude_device_id` BEFORE the scope check. `go_online`'s FINAL tournament frame self-excludes (`exclude_device_id=request.device_id`); the resolved-users/decks/sanctions/ratings broadcasts above it intentionally still reach the device (it lacks them). Excludes the whole device (all tabs), keyed on client-supplied param — sound because offline mode is single-tab (WASM writes IDB directly) and self-exclusion can only DROP a frame to YOUR OWN device, never leak data or affect another device. `GoOnlineRequest.device_id: str` is required; bot connections (`device_id=None`) never match.
- **Frontend in-flight guard (tab-precise backstop):** `goingOnlineUids` Set in offline.svelte.ts; `goOnline()` add-in-try / delete-in-finally. `lostOfflineLock` returns false whenever `goingOnlineUids.has(uid)` — BROADENED from the earlier `offline_mode !== true` narrowing. During an in-flight go-online ALL SSE lock-state frames for that tournament are ignored; the HTTP response (success / 410 / 409) is the SOLE authority.
- **409 reconciliation:** `goOnline` catch now treats BOTH 410 AND 409 as "session ended" → `clearOfflineState` + lock-lost warning (was 410-only; 409 fell through to a generic toast and left the device wedged offline). Discarding this device's unsynced work on 409 (another device took over) is deliberate — reclaiming is a separate explicit force-takeover, not a silent clobber from the sync path.

**Why both layers:** server exclusion kills the self-echo class at the source even if a future code path bypasses the guard; the guard is tab-precise AND collapses a concurrent force-unlock/takeover frame into the single 410/409 warning the response path raises (no double-report).

**How to apply / residual trap (the in-flight window):**
- The broadened guard now drops even a GENUINE concurrent force-unlock/takeover SSE frame during the in-flight window, relying on the HTTP response to reconcile. This is sound ONLY because go_online always terminates with success (saveTournament overwrites) / 410 (force-unlock) / 409 (takeover) — each runs clearOfflineState or applies authoritative state. The bounded gap: if the network DROPS the go_online request (no HTTP response) AND a real takeover/unlock frame arrived during that window, the frame was ignored and the device stays marked offline until the NEXT SSE frame or reconnect re-delivers offline_mode (now that goingOnlineUids is cleared in finally). Acceptable: any later tournament frame or reconnect catch-up re-runs lostOfflineLock and reconciles; no permanent wedge. Preserve the finally-delete so the guard can never stick.
- If you add a new persistent reason to ignore lock frames, do NOT widen goingOnlineUids beyond the request lifetime — its safety depends on being short-lived and finally-cleared.
- Keep the device_id param wired on EVERY /stream connect (incl. reconnect — sync.ts builds the URL fresh each time, so it's covered). A reconnect that drops device_id would re-expose the self-echo on the next go-online.
- **Post-commit tournament rewrite is invisible to the initiating device.** The go_online HTTP response returns `updated` — the tournament as built at the FOR-UPDATE commit point. Any server-side tournament write that happens AFTER that (the offline-sanction feature's `_apply_sanction_to_tournament(uid)` authoritative standings recompute at ~tournaments.py:2383, or any future post-commit rewrite) produces a NEWER DB row than the response carries, and its SSE echo is dropped on the initiating device by goingOnlineUids (self-echo suppression) — so that device persists the pre-rewrite response via saveTournament and never sees the recompute until the next unrelated tournament frame / reconnect resync. Harmless when client WASM recompute == server recompute (the single-device norm), but silently diverges when they differ (e.g. a second organizer issued a sanction ONLINE on the same tournament during the offline window — sanction SSE frames are NOT offline-skipped in sync.ts, only `singleType==='tournament'` frames are). Fix pattern: return the POST-recompute tournament (re-read `get_tournament_by_uid(uid)` after the recompute, or have the helper return it) so the response is once again the sole authority. Same class as [[go-online-self-echo-409-gap]]'s "HTTP response is sole authority in-flight" invariant — a post-commit rewrite breaks it.
